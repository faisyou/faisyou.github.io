Two-way TLS identity

Executive summary

  • Normal TLS authenticates the server to Genesys.
  • Mutual TLS adds authentication of the client.
  • For an mTLS-enabled Genesys Web Services Data Action, the customer endpoint requests a client certificate during the TLS handshake.
  • The customer endpoint must be able to validate and trust the certificate presented by Genesys.

Mutual TLS adds client auth

Genesys Cloud
⇄
Customer server
  1. Customer server presents its server certificate.
  2. Genesys validates the server certificate.
  3. Customer endpoint requests a client certificate.
  4. Genesys presents its client certificate.
  5. Customer validates and trusts the Genesys client certificate.
  6. The TLS session is established.
  7. The HTTP request is sent.
mTLS adds client-certificate authentication on top of everything normal HTTPS already does. It does not replace HTTP-level authentication such as an API key or OAuth token.

Each side protects its own private key. Each side presents a certificate that proves possession of the corresponding private key.
The customer does not need the Genesys private key — only the trust configuration to validate the Genesys client certificate. Genesys does not need the customer’s private key — only the ability to trust and validate the customer’s server certificate.

Ownership ≠ trust

Who trusts it?

Customer
Trusts / validates the Genesys client certificate
Genesys
Trusts / validates the customer server certificate
  • The party that owns a certificate does not validate it themselves — the receiving side does.
  • Each side keeps its own private key secret.
  • Each side is responsible for validating the certificate presented by the other side.
  • Trust is normally established using a configured trusted CA or certificate chain, depending on the endpoint architecture.
Certificate ownership tells us who controls the identity. Trust configuration tells us who is willing to accept that identity.

How do we prove Genesys actually sends the client certificate?

Genesys Data Action
↓ TLS handshake
Test HTTPS server
  • Did a client certificate arrive?
  • What certificate was presented?
  • Was it considered authorized?
  • Did the TLS handshake complete?

The cleanest test is a purpose-built HTTPS server that:

  • requests a client certificate,
  • initially does not reject an untrusted certificate,
  • logs the presented certificate,
  • reports whether a certificate was received,
  • reports whether it was authorized, and
  • can later be switched to strict certificate validation.
First prove certificate presentation. Then prove certificate trust.

Goal: prove Genesys can reach the AWS endpoint.

EC2 is recommended for the first diagnostic because it offers:

  • direct TLS termination in Node.js,
  • the easiest way to inspect the peer certificate,
  • no hidden TLS behavior behind a load balancer, and
  • straightforward control of Node.js TLS settings.
An ALB, API Gateway, or other managed architecture may be appropriate for production — direct TLS termination on EC2 makes the diagnostic behavior easier to observe.

  1. Create EC2 instance.

What this test proves — and what it doesn’t

This test proves

  • AWS endpoint is reachable.
  • Genesys can establish TLS with the endpoint.
  • The customer endpoint can observe whether a client certificate is presented.
  • The presented certificate’s metadata can be captured.
  • The customer can validate trust in the presented certificate.
  • The Data Action can complete an HTTP request.

This test does not automatically prove

  • Production certificate lifecycle is correctly managed.
  • Production certificate rotation behavior.
  • High availability.
  • Production gateway behavior.
  • Every possible Genesys region / path.
  • Application authorization policy.
  • Security of the entire production integration.

From test to production

Test

  • EC2
  • Node.js diagnostic server
  • Direct TLS termination
  • Diagnostic certificate logging
  • Temporary relaxed certificate validation during initial observation

Production

  • Managed certificate lifecycle
  • Protected private keys
  • Strict trust policy & certificate validation
  • Certificate rotation
  • Monitoring & audit logging
  • High availability, controlled ingress
  • API gateway / load balancer where appropriate
  • Least-privilege authorization
Do not carry rejectUnauthorized = false into production.

Executive conclusion

  1. mTLS adds client authentication to HTTPS.
  2. For a Genesys Web Services Data Action, the customer endpoint can validate the client certificate presented by Genesys during the TLS handshake.
  3. The fastest way to remove uncertainty is to run a controlled AWS HTTPS endpoint that observes the client certificate and then progressively enforces trust.

Appendix A

Full Node.js server source

// mtls-test-server.js // Minimal diagnostic HTTPS server for observing and validating // TLS client-certificate presentation from Genesys Cloud. // // Stage 2 (observe presentation): // STRICT_TLS unset or "false" -> rejectUnauthorized: false // Stage 3 (enforce trust): // STRICT_TLS=true, CA_FILE set -> rejectUnauthorized: true const https = require('https'); const fs = require('fs'); const path = require('path'); const PORT = process.env.PORT || 443; const STRICT_TLS = process.env.STRICT_TLS === 'true'; const CERT_DIR = process.env.CERT_DIR || path.join(__dirname, 'certs'); const options = { // Customer server certificate and private key. // The private key never leaves this host. key: fs.readFileSync(path.join(CERT_DIR, 'server-key.pem')), cert: fs.readFileSync(path.join(CERT_DIR, 'server-cert.pem')), // Ask the connecting client (Genesys Cloud) for a certificate. requestCert: true, // Stage 2: false -> observe the certificate without rejecting the // connection while trust is not yet configured. // Stage 3: true -> reject connections whose client certificate is // not signed by a CA listed in `ca` below. rejectUnauthorized: STRICT_TLS, }; // Stage 3 only: the CA (or chain) used to validate the Genesys client // certificate. Point this at the appropriate trust anchor once known. if (STRICT_TLS) { const caFile = process.env.CA_FILE || path.join(CERT_DIR, 'ca.pem'); options.ca = fs.readFileSync(caFile); } function logLine(fields) { console.log(JSON.stringify({ time: new Date().toISOString(), ...fields })); } const server = https.createServer(options, (req, res) => { // true -> include the full certificate chain, not just the leaf. const peerCert = req.socket.getPeerCertificate(true); const presented = peerCert && Object.keys(peerCert).length > 0; const authorized = req.client.authorized === true; const diagnostic = { clientCertificatePresented: presented, authorized, authorizationError: req.client.authorizationError || null, subject: presented ? peerCert.subject : null, issuer: presented ? peerCert.issuer : null, serialNumber: presented ? peerCert.serialNumber : null, validFrom: presented ? peerCert.valid_from : null, validTo: presented ? peerCert.valid_to : null, fingerprint256: presented ? peerCert.fingerprint256 : null, timestamp: new Date().toISOString(), }; logLine({ event: 'request', path: req.url, remoteAddress: req.socket.remoteAddress, ...diagnostic, }); res.writeHead(200, { 'Content-Type': 'application/json' }); res.end(JSON.stringify(diagnostic, null, 2)); }); server.on('tlsClientError', (err, socket) => { logLine({ event: 'tlsClientError', message: err.message, remoteAddress: socket.remoteAddress, }); }); server.listen(PORT, () => { logLine({ event: 'listening', port: PORT, strictTls: STRICT_TLS, }); });

The code separates requestCert from rejectUnauthorized and controls both through a single STRICT_TLS flag, so the same file carries the server from Stage 2 (observe) through to Stage 3 (enforce) without a rewrite.

Appendix F

Independent testing with curl

curl https://mtls-test.example.com/test

A successful response proves the endpoint is publicly reachable, TLS server-certificate validation succeeds against curl’s trust store, and the endpoint is responding to HTTP requests.

curl without a client certificate is useful for verifying the server itself. A client-certificate test can reproduce a full client-authentication scenario where appropriate:

curl --cert client-cert.pem --key client-key.pem \ https://mtls-test.example.com/test
Appendix G

OpenSSL diagnostic commands

openssl s_client -connect mtls-test.example.com:443 -showcerts

Look for:

  • the server certificate
  • the certificate chain
  • the negotiated TLS version
  • a client-certificate request (for example, “Acceptable client certificate CA names” or a CertificateRequest message)
  • the overall handshake result

An OpenSSL test does not reproduce Genesys’ exact TLS client behavior — it verifies the server side of the handshake.
